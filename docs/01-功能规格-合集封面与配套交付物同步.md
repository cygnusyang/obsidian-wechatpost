## 0. 一句话

插件目前只做一件事——**把正文发出去**。这份规格要让它同时管住发布时的三件元数据：

1. **合集去哪**：从笔记属性读，逐篇精确落位，不再靠硬编码。
2. **封面用哪张**：用本地已有的封面 PNG，取代不靠谱的 AI 配图。
3. **交付物跟哪走**：把 `assets/` 与 `配套交付物/` 里的成品按篇同步到该去的地方。

三件事今天全部靠**手工或硬编码**完成。以下是证据。

三个功能的落点都跨了两个仓库：**插件准备数据，引擎执行动作**。功能二、三的"点浏览器"那半边
必然在 `wechatpost-mcp` 里——这一点在 §5 有明确的责任划分。

> **v1.1 变更**：三个功能均已落地代码。`galleryImages`（金句卡上传图片库）实现阶段**撤回**，
> 理由见 §5.1。新增 §3.5 覆盖率实测：功能三当前只覆盖 36% 的在用文章，功能二能自动化的
> 也只有 36% —— 这两个数字决定它们今天到底能帮上多少。

## 1. 现状核查

### 1.1 现有链路

```
Obsidian 笔记 (.md)
  ├─ frontmatter  ──► 改造前只用到 title / description（auto_publish.mjs 至今只用这两个）
  └─ 正文        ──► wechat_publish ──► PlaywrightService.createDraftInBrowser()
                                              ├─ Step 7  填标题
                                              ├─ Step 8  填作者
                                              ├─ Step 9  填正文（含正文内嵌图，走 setInputFiles 上传）
                                              ├─ Step 10 填摘要
                                              ├─ Step 11-17  ★ 封面：强制走「AI 配图」
                                              ├─ Step 18 原创声明
                                              ├─ Step 19 赞赏
                                              └─ Step 20 ★ 合集：单个字符串，精确匹配
```

### 1.2 三个缺陷（均有据可查）

#### 缺陷 A · 合集名硬编码，与运营规则冲突

- 自动化脚本 `wechatpost-mcp/auto_publish.mjs:23` 写死：

  ```js
  const COLLECTION = '工程那些事';
  ```

  队列里**每一篇**都带着这一个合集名发布。
- 但《关键词自动回复配置清单》§合集设置明确：

  > 系列拆分后，读者追更走**公众号合集**……发布接口的 `defaultCollection` 只支持**一个**默认合集；两条系列发布时需按篇指定合集名，不要依赖全局默认。

  《运营总纲》§四 也写着「**每篇入对应系列合集**」。
- 已登记的合集至少有：`模具 DFM 深挖系列`、`模流分析能力系列`、`测量实战系列`。
- 结论：**规则说逐篇指定，实现是全局写死**。这是本功能要修的第一件事。

#### 缺陷 B · 封面强制走 AI 配图

- 引擎 Step 11–17（`src/services/PlaywrightService.ts:3092-3172`）是**唯一的封面路径**：

  ```
  click .icon20_common.add_cover (×2) → clickAiCoverEntry() → 用标题当 Prompt
  → 点「开始创作」→ 等 .ai-image-item-wrp 出现 → 选第一张 → 点「使用」→ 点「确认」
  ```

- `clickAiCoverEntry()`（同文件 `:2558`）候选选择器只认 `a.js_aiImage`、`链接名=AI 配图`、`.pop-opr__button(含 "AI 配图")`。**没有任何「本地上传」分支**。
- 而本地封面是成套存在的、质量可控的。以 `28-Usability易用性系列` 为例，`assets/封面/` 里 `00-封面.png` ~ `10-封面.png` 齐备，尺寸 **1080×460（2.35:1）**，单张约 42–52 KB。
- `03-发布配置/发布备注.md` 已经写明这一步是手工的：

  > 各篇金句卡 SVG 仍保留在 `assets/` 目录，**发布时在公众号编辑器中设为封面图**（SVG 需先导出为 PNG 上传）。

- 结论：**封面是本地产出、手工上传**。插件只要把这一步接过来，就能消灭每次发布的一次手工点击。

#### 缺陷 C · 配套交付物完全没有被发布链路感知

- `assets/` 与 `配套交付物/` 里的成品已成规模，命名规整（见 §3.1），但插件与引擎**都不读这两个目录**。
- 一个容易踩的坑：`配套交付物/` 里大部分是 **`.md` / `.xlsx`**，而公众号**不支持文件附件**。所以「把配套交付物同步上传到公众号」这句话必须先分型——图片能进图片库，表格不能，只能走金山文档链接（这也是现有「排气槽设计参考」规则用的方式）。
- 结论：本功能不是「一律上传」，而是**按文件类型分流**（见 §3.2）。

### 1.3 关于属性名 `catalog` 的事实

需求里说「读笔记属性里的 `catalog`」。核查结果：

- 全量统计 `08-公众号/01-文章/**/*公众号版.md`（**368 篇**，含 `_backup_20260923/`）：

  | 字段 | 命中 |
  |---|---|
  | 有 frontmatter | 367 / 368（唯一例外是 `_backup_20260923/04-材料与手感系列/01-TPE同样30A软硬不一-公众号版.md`，无头） |
  | `title` | 367 |
  | `date` | 367 |
  | `category` | 367 |
  | `tags` | 367 |
  | `description` | 367 |
  | **`catalog`** | **0** |
  | **`collection`** | **0** |

- 全库检索 `catalog:` → 只命中知识库根目录的 `catalog.yaml` 体系（`tools/sync_catalog_articles.py` 维护的阅读目录），与公众号合集无关。
- 现有 `category` 的值是**主题类目**，全库共 **20 个不同取值**：`注塑与材料` / `硬件研发与供应链` / `硬件产品与市场` / `DFX研发设计` / `DFC成本` / `DFE环境设计` / `DFD可拆解` / `DFR可靠性` / `DFL物流包装` / `DFQ质量设计` / `Robustness稳健性设计` / `DFT可测试性` / `可维修性设计` / `服务支持设计` / `安全设计` / `网络安全设计` / `合规设计` / `供应链设计` / `可升级设计` / `易用性设计`。

  而后台合集名是 `模具 DFM 深挖系列` 这类**系列名**。20 个类目 vs 28 个系列 —— 两者**不是一回事**，不能拿 `category` 直接当合集名。

**因此本规格把 `catalog` 定义为「新增的、专门承载合集名的属性」**，并：

- 属性名**可配置**（设置项 `合集属性名`，默认 `catalog`）；
- 兼容别名 `collection`；
- **不**回退到 `category`（语义不同，静默回退会产生「以为配上了、其实没配上」的假成功）。

## 2. 功能一 · 笔记属性 → 公众号合集

### 2.1 契约

| 项 | 定义 |
|---|---|
| 属性名 | `catalog`（可配置，别名 `collection`） |
| 值 | 公众号后台**已存在的合集名**，字符串 |
| 匹配 | 精确匹配（引擎 `collectionOptionByName()` 已是 `getByText(name, { exact: true })`），不做模糊、不做近似 |
| 作用域 | 单篇笔记 |

示例：

```yaml
---
title: "凭什么说这版更好用"
date: 2026-09-23
category: "易用性设计"
catalog: "Usability 易用性设计系列"     # ← 新增：公众号合集名
tags: [DFX, 易用性, 公众号, 任务度量, 样本边界, 改版验证]
description: "没有样本边界的好评不是证据……"
---
```

### 2.2 取值优先级链

```
1. 笔记 frontmatter[catalog]            ← 首选，逐篇精确
2. 笔记 frontmatter[collection]         ← 兼容别名
3. 插件设置 defaultCollection            ← 兜底（保留原行为）
4. 不传 → 引擎跳过 Sort 20，不挂合集
```

### 2.3 失败处理（必须显式）

| 情形 | 行为 |
|---|---|
| 属性缺失 | 落到下一级；最终无值则**不挂合集**，Notice 提示「本篇未指定合集」 |
| 属性有值但后台无此合集 | 引擎已保证**只精确匹配、绝不静默挂别的合集**，仅告警。插件在 Notice 中回显解析到的合集名，便于发现拼写错误 |
| 属性值含首尾空白/全角空格 | 归一化后使用（trim + 全角空格转半角） |

### 2.4 与自动化脚本的关系

`auto_publish.mjs:23` 的 `COLLECTION` 常量应同步改为「从 frontmatter 读，缺失才用默认」，与插件共用同一套优先级链。否则 Obsidian 手动发和 launchd 自动发会走进两个不同的合集。

### 2.5 已实现内容（插件侧）

- 新增 `src/frontmatter.ts`：解析 frontmatter（**不引入 YAML 依赖**，只处理 `key: value` / 引号 / 折行的引号值 / 数组字面量），提取 `catalog` 等字段。
- 新增 `resolveCollection()`：实现 §2.2 优先级链 + §2.3 归一化（含全角空格 `\u3000` / `\u00a0` 等异体空格）。
- 新增 `describeCollection()`：把取值来源渲染成可读一行，用于 Notice 回显。
- `src/settings.ts` 新增 `collectionProperty`（默认 `catalog`）。
- `src/settingsTab.ts` 新增「Collection property」设置项，并把原「Default collection」改标为兜底用途。
- `src/main.ts`：`publishCurrentNote()` / `saveCurrentNoteAsDraft()` 合并为 `publishNote(publish)`，改用解析结果，Notice 回显来源：

  ```
  Publishing "凭什么说这版更好用"...
  合集：Usability 易用性设计系列（来自 frontmatter.catalog）
  ```

- 附带改进：`digest` 优先取 frontmatter 的 `description`（与《发布备注》「原核心观点句由 `description` 承载」一致），而非正文开头硬切。

**实测验证**（打包本模块后对真实笔记全量执行）：

```
笔记总数（公众号版）  : 368
frontmatter 解析成功  : 367 / 368   ← 唯一未命中是 _backup_20260923/ 下的备份件，无头
catalog / collection  : 0 / 0        ← 全库尚无该属性，需补（见 §8 P3）
```

优先级链用例（全部通过）：

| 输入 | 解析结果 |
|---|---|
| `category: 易用性设计`，无 catalog | `合集：工程那些事（来自 插件默认值）` |
| `catalog: Usability 易用性设计系列` | `合集：Usability 易用性设计系列（来自 frontmatter.catalog）` |
| `catalog:` 空 + `collection: 模流分析能力系列` | `合集：模流分析能力系列（来自 frontmatter.collection）` |
| 属性名配置为 `collection` | `合集：测量实战系列（来自 frontmatter.collection）` |
| `catalog: "　模具 DFM 深挖系列　"`（全角空格） | `合集：模具 DFM 深挖系列（来自 frontmatter.catalog）` |
| 兜底值也为空 | `合集：（未指定）` —— 引擎跳过挂载，不挂错 |
| 只有 `category: 注塑与材料` | `合集：（未指定）` —— **不回退到 category** |

**未实现**：`auto_publish.mjs` 的同步改造（属引擎仓库，见 §8 P3）。

## 3. 功能二 · 配套交付物同步

### 3.1 目录与命名契约（实测）

以 `08-公众号/01-文章/28-Usability易用性系列/` 为准（其余系列同构）：

```
28-Usability易用性系列/
├── 08-凭什么说这版更好用-公众号版.md      ← 文章，文件名前缀 = 两位编号
├── assets/
│   ├── 08-任务度量.svg                    ← 正文配图源文件
│   ├── png/08-任务度量.png                ← 1080×785，正文用位图
│   ├── 封面/08-封面.png                   ← 1080×460 (2.35:1)，封面
│   ├── 封面/08-封面.svg                   ← 封面源文件
│   ├── 金句卡/08-金句卡-竖版.png          ← 1080×1440，金句卡
│   └── 金句卡/08-金句卡-竖版.svg
└── 配套交付物/
    ├── 08-任务度量记录表.md               ← 表格模型（Markdown）
    └── 08-任务度量记录表.xlsx             ← 表格成品（Excel）
```

**核心契约：两位编号前缀是唯一的归篇键。** 文章 `NN-*.md` 的配套件一律为 `NN-*`。当前系列内编号连续、无缺号。

### 3.2 文件类型 → 去向矩阵（关键约束）

公众号**不是网盘**。本功能必须先分型，否则会设计出一个跑不通的流程：

| 来源 | 类型 | 体积实测 | 去向 | 可否自动 |
|---|---|---|---|---|
| `assets/封面/NN-封面.png` | PNG | 42–52 KB | **设为文章封面**（走功能三） | 可（需引擎扩展） |
| `assets/金句卡/NN-金句卡-竖版.png` | PNG | 55–79 KB | 上传**图片库**，备用（分享图 / 文末图） | 可（需引擎扩展） |
| `assets/png/NN-*.png` | PNG | 175–205 KB | 正文配图。**已由引擎内嵌上传**，不重复处理 | 已具备 |
| `配套交付物/NN-*.md` | Markdown | 3–5 KB | ❌ **公众号不支持文件附件**。转金山文档链接，走关键词自动回复 | 不可，需人工转链 |
| `配套交付物/NN-*.xlsx` | Excel | 9–10 KB | ❌ 同上。行业既有做法：关键词回复推送金山文档直链（参照「排气槽设计参考」规则） | 不可，需人工转链 |

**体积约束**（可引用）：引擎内嵌图片上限 `WECHAT_ARTICLE_IMAGE_MAX_BYTES = 900 * 1024`（`PlaywrightService.ts:30`）。上表所有 PNG 均远低于该值，无体积风险。

### 3.3 匹配规则

```
输入：文章绝对路径 A = <series>/NN-<title>-公众号版.md
1. seriesDir = dirname(A)                             → <series>/
2. 提取编号 prefix = NN（取文件名开头两位数字）
3. 候选集：
   - <series>/assets/封面/NN-*.png
   - <series>/assets/金句卡/NN-*.png
   - <series>/配套交付物/NN-*.md / NN-*.xlsx
4. 一律按「文件名以 NN- 开头」精确前缀匹配；不用模糊匹配、不用编辑距离
5. 编号缺失或不连续 → 不猜，报告「未找到配套件」并列出该目录下实际存在的编号
```

### 3.4 同步动作定义

| 产物 | 动作 |
|---|---|
| 封面 | 作为 `coverImagePath` 传给发布（功能三） |
| 金句卡 | 上传图片库，返回素材 URL；写入发布回执 |
| 交付物（.md/.xlsx） | **不上传**。列出清单 + 提示「需转金山文档并配关键词回复」，避免制造「已同步」的假象 |
| 回执 | 发布完成后在插件内展示一张「本篇配套件处理结果」表，逐项标 `已上传 / 已跳过 / 缺失` |

**设计红线：不做静默跳过。** 找不到的配套件必须在回执里以「缺失」出现，否则「同步过了」这句话就又变成不可核对的口头承诺。

### 3.5 覆盖率实测（决定这个功能到底能帮上多少）

用 `src/deliverables.ts` 扫描全库（`08-公众号/01-文章/`，2026-09-23）：

| 指标 | 数量 | 占在用文章比 |
|---|---|---|
| `*公众号版.md` 总数 | 368 | — |
| 其中在 `_backup_*/`、`_标题改写_*/` 内 | 87 | — |
| 其中在 `配套交付物/` 内（关键词回复素材图文，非独立文章） | 3 | — |
| **在用的正式文章** | **279** | 100% |
| 有本地封面 `assets/封面/NN-*.png` | 101 | **36%** |
| 有金句卡 `assets/金句卡/NN-*.png` | 100 | **36%** |
| 有正文配图 `assets/png/NN-*.png` | 121 | 43% |
| 有配套交付物 `配套交付物/NN-*` | 246 | **88%** |

按系列看，封面成套的是 `20-DFT` 一路到 `28-Usability`（9 个系列各 11 篇齐备），加上
`10-DFX研发设计系列` 与 `13-DFD可拆解系列` 各 1 张；**其余 16 个系列零封面**。

**由此得出两条硬结论：**

1. **功能三今天只覆盖 36% 的在用文章。** 剩下 64% 发布时仍然落到 AI 配图（或按设置中止）。
   想让"不再用 AI 封面"成立，先把 `assets/封面/` 补齐到那些老系列。
2. **功能二听起来最大，可自动化的部分反而最小。** 88% 的文章有配套交付物，但那些是
   `.md` / `.xlsx`，公众号不支持文件附件 —— **真正能自动上传的只有封面与金句卡（各 36%）**。
   剩下 88% 的交付物只能转金山文档链接，"同步"二字对它们只能兑现成"提醒你去转链"。

## 4. 功能三 · 本地封面上传

### 4.1 已实现的流程（替换 Step 11–17 中的 AI 分支）

**引擎侧已实现** `PlaywrightService.setLocalCoverImage()`，挂在 Step 11 之后：

```
Step 11    click .icon20_common.add_cover (×2)           ← 原样保留
Step 11a   若 coverImagePath 有效 → setLocalCoverImage()：
           (a) 弹层里已挂载的 file input → setInputFiles → 等图片数增长
           (b) 「本地上传 / 上传图片 / 上传封面」入口 → 点击后再扫 file input
           (c) 「从图片库选择 / 图片库」入口 → 进入后再扫 file input
           命中后：选中新缩略图 → 若有「确认」则点击
           全部未命中：dump 弹层真实 file input 与可见按钮文案，返回 false
Step 12-17 仅在 11a 返回 false 时执行（AI 配图兜底）
```

设计要点：

- **自诊断**：第一次真机跑，无论成功与否都会打印证据。命中时打印
  `[COVER] Cover image accepted via <selector>`；未命中时打印 `[COVER-DIAG]`，
  给出弹层里**真实存在**的 file input（含 `accept` / `name` / 可见性）与可见按钮文案。
  也就是说选择器只需要一轮真机就能钉死，不存在"猜第二轮"。
- **零侵入**：`coverImagePath` 未传时整段不执行，AI 流程原样保留。
- **硬错误与软失败分开**：文件不存在 → 抛错（配置问题）；弹层无本地上传入口 → 返回
  `false`（平台问题），由调用方按 `coverFallbackToAi` 决定兜底还是中止。

### 4.2 发布时的选择交互

需求：「**发布新文章的时候，需要去选择这个封面图片**」。已实现为 Obsidian `SuggestModal`
（`src/coverPicker.ts`）：

| 级别 | 行为 |
|---|---|
| 默认 | **每次都弹**，自动匹配的 `NN-封面.png` **排在第一位并默认高亮** —— 回车即确认 |
| 关闭提问（设置项） | 唯一命中时静默采用；命中多于 1 个时仍然弹窗（不替用户猜哪张） |
| 候选为空 | 不弹窗，Notice 说明「未找到本地封面」，按兜底设置处理 |

候选清单与排序：

1. `assets/封面/NN-*.png`（标注「← 自动匹配」）
2. `assets/金句卡/NN-*.png`（金句卡也常被当封面/分享图用）

每项显示：文件名、类别、**PNG 实测尺寸**（直接读 IHDR，`readPngSize()`）、体积。键盘可搜。

**兜底链**：未选到本地封面 → `coverFallbackToAi`（默认 true）则退回 AI 配图；
设为 false 则中止发布并抛错。**不做「悄悄用 AI 图」**——封面是发布里最显眼的一环，
静默替换等于骗人。

## 5. 架构影响与责任划分

插件是**薄客户端**，不自己驱动浏览器（见 README「Why this architecture」）。因此三个功能的落点必须分清：

| 能力 | 插件侧（`obsidian-wechatpost`） | 引擎侧（`wechatpost-mcp`） |
|---|---|---|
| 读 frontmatter `catalog` | ✅ 已实现 | — |
| 解析合集优先级链 | ✅ 已实现 | — |
| 扫描 `assets/`、`配套交付物/` | ✅ 已实现（`src/deliverables.ts`） | — |
| 封面候选选择弹窗 | ✅ 已实现（`src/coverPicker.ts`） | — |
| **把本地图片设为封面** | ✅ 传 `coverImagePath` | ✅ 已实现（`setLocalCoverImage()`，待真机核对选择器） |
| **上传金句卡到图片库** | 只传清单 | ⏸ **本期不做**，理由见 §5.1 |
| 交付物转金山文档 | ✅ 出提示清单 | — （平台不支持，人工） |

**关键结论：「在这个插件里加功能」这句话，对功能二、三只对了一半。** 真正点浏览器的那半边在 `PlaywrightService` 里。规格按「插件准备数据 → 引擎执行动作」切分。

### 5.1 为什么本期不做 `galleryImages`（上传金句卡到图片库）

原规格 §6.1 曾列入 `galleryImages`（把金句卡等上传到图片库）。实现阶段复核后**撤回**：

- 引擎里**已验证可用**的图片上传路径只有一条 —— `tryUploadImageAtCursor()` 的
  `setInputFiles` 把图片**插进正文光标处**。正文图片本来就能用 Markdown 引用表达，
  引擎已支持，无需新参数。
- 「只上传到图片库、不插入正文」是另一条未验证的交互路径，收益也不确定：金句卡的实际用途
  （分享图 / 文末图 / 社群转发）尚未定，**先把上传通道修好会锁死错误的使用方式**。
- 按 §3.4 的红线，宁可在回执里把它标为「未处理」，也不做一个说不清去向的上传口。

待定项（需要 cygnus 拍板）：**金句卡在发布链路里到底承担什么角色？** 确认后再补协议。

## 7. 边界与已知约束

| 类别 | 约束 |
|---|---|
| 平台 | 合集必须**先在后台创建**，否则发不进去（引擎只精确匹配，找不到就跳过并告警） |
| 平台 | 公众号**不支持文件附件**，`.md` / `.xlsx` 无法直接同步（见 §3.2） |
| 平台 | 一篇文章**最多 1 个合集**（弹层原文：「每篇文章最多添加1个合集」） |
| 平台 | 内嵌图片单张 ≤ 900 KB（`PlaywrightService.ts:30`） |
| 本地 | `assets/封面`、`assets/金句卡`、`assets/png` 三个子目录**尚未在全部系列建齐**，16 个系列零封面（见 §3.5） |
| 本地 | **在用的 279 篇里只有 101 篇（36%）有本地封面** —— 这是功能三当前的实际天花板 |
| 本地 | `配套交付物/` 的 `.xlsx` 与 `.md` 是否成对，各系列不一致，需按 §3.4 出回执核对 |
| 扫描 | 关键词回复素材图文（`NN-检查表-公众号版.md`）也放在 `配套交付物/` 内，扫描时会被当作交付物命中；这是**正确的**（它确实是配套件），但别把它当正文文章 |
| 格式 | 封面源文件为 SVG，公众号只收位图，**必须用同目录的 PNG**（本地产出流程已备好） |
| 环境 | 插件 `isDesktopOnly: true`（需 spawn 外部 Chromium） |
